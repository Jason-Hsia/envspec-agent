垂直领域 Agent · 项目方案

环保规范检索 Agent RAG + Tool Use，面向环境工程的学习与工作场景，自带评测闭环

一套可运行、可评测、可持续迭代的生态环境标准问答系统。核心不是"接个大模型做检索"， 而是把环保领域两个绕不开的硬约束——标准会失效与限值附条件—— 转化成可被指标度量、可被门禁拦截的工程问题。

01项目定位与核心判断

先说清楚为什么这件事值得做、以及它区别于"套壳 RAG"的地方在哪里。

1.1 领域的两道硬约束

约束一：标准会失效

国标与行标持续修订，被替代的版本仍会长期留在语料、教材和旧报告里。 GB 18597-2001 的条文措辞甚至比 2023 版更贴合"贮存设施选址"这类提问词， 向量检索会优先命中失效版本。用户拿到一个数值，却不知道它早已作废。

约束二：限值附条件

同一个污染物，地表水按 Ⅰ–Ⅴ 类分档、废水按一级/二级/三级分档、湖库与河流不同、 冬季与常规时段不同、地方标准严于国标。少说一个条件，答案就是错的。

核心判断

这两条约束恰恰是 Tool Use 不可替代的理由。时效性只能靠查状态表判定， 限值只能靠结构化表查询取值 —— 都是确定性操作，不该交给语言模型的记忆与推理。 因此本项目的技术重心是：把该确定的事交给代码，把该表达的事交给模型， 并用一套指标把两者各自的贡献分开度量。

1.2 与传统 RAG 方案的差异

维度常规 RAG 方案本方案

3.1 知识库构建：为检索而设计，不是为存储而设计

数据源

  • 国家层面：生态环境部标准库（mee.gov.cn/ywgz/fgbz）——国家标准与行业标准全文，含发布/实施日期、替代关系公告
  • 标准元数据：全国标准信息公共服务平台（std.samr.gov.cn）——用于交叉校验标准号的现行/废止状态
  • 地方标准：各省生态环境厅地方标准栏目，例如浙江省 DB33/ 2169-2018
  • 管理名录：《建设项目环境影响评价分类管理名录》等非标准类规范性文件

接入方式统一为「官方数据源适配器」——每个发布机构的 PDF 版式不同，适配器各自负责版式解析， 输出统一的中间结构。这是 P0 阶段最大的工作量来源，也是唯一无法用模型绕过去的部分。

切分策略：按条文层级，而非固定长度

以条文编号（4.1 / 6.1.1）与表号（表1）为切分锚点， 保留章节面包屑写入元数据。固定长度滑窗会把一条条文劈成两半， 既破坏了"引用必须落到条文号"的可溯源要求，也会让限值与其适用条件被拆散。

已识别的工程坑

标准号归一化：GB 3838—2002（全角破折号）、GB3838-2002（无空格）、 gb 3838 - 2002（多余空格）会被当成三个不同标准，导致引用关系图断裂、时效性校验漏判。 必须在入库时统一归一化。

数据可信度必须显式建模

本仓库的 data/standards_seed.json 是结构演示数据，每条记录带 verified 字段。 生产环境必须以官方文本重新灌入并置 verified=true； 评测集同样不得建立在校验数据之上——用未核验的数据证明系统准确，是自欺。

3.2 检索增强：三处不放入门教程的设计

① 查询理解先行，元数据过滤前置

先抽取 7 类槽位：污染物 · 介质 · 等级 · 属地 · 行业 · 标准号 · 意图， 在元数据层做硬过滤，再进向量计算。这一步拦掉的是最致命的一类错误—— "问废水排放标准，答成地表水质量标准"。过滤之后再算相似度，也让算力不被浪费。

② RRF 融合而非加权求和

BM25 分数与向量余弦分数量纲不可比，加权系数需要反复调参且跨查询不稳。 RRF（Reciprocal Rank Fusion）只用排名、不用分数，跨查询稳定性显著更好。 环保语料还特别依赖 BM25：用户大量输入 GB 3838-2002 表1 COD Ⅲ类 这类强符号查询， 判别信息全在罕见 token 上，稠密向量表达不了。

③ 时效性参与重排

现行标准在重排时加分，被替代标准降权但不删除。 保留是为了让下游能主动提示"你查的这条已被替代"——用户往往正是拿着旧报告来核对的。 降权则保证正确的现行版本排在前列。

代价最高的一类 bug：罗马数字等级前缀误匹配

朴素子串匹配 alias in query 会让 "iii类" 同时命中 "i类"、"ii类"、"iii类"， 于是"地表水Ⅲ类 COD 限值"被解析成 Ⅰ/Ⅱ/Ⅲ 三个等级，等级过滤失效、取到错误档位。 正确做法是正则 + 有序候选（长候选优先），并按介质选择对应的等级体系：

# 长候选必须排在前面，否则 "iii" 会被 "i" 抢先吃掉
_RE_WATER_GRADE = re.compile(r"(iii|ii|iv|i|v)\s*类")

# 声环境功能区 0-4 类与地表水 Ⅰ-Ⅴ 类语义完全不同，必须按介质分流
def extract_grades(low, media):
    if "noise" in media:      # "2类" → 声环境功能区 2 类
        ...
    if "water_surface" in media: # "Ⅲ类" → 地表水 Ⅲ 类
        ...

④ 查询分解

对比类问题（"地表水Ⅲ类 COD 限值与废水一级排放 COD 限值有什么区别"）不存在唯一适用标准， 必须拆成多路查询分别取证。但不能只看"出现多个介质"就判定为对比题—— "排入地表水Ⅲ类水域的工业废水执行几级标准"同样同时出现地表水与废水， 它是单一问题（地表水只是用来定级的受纳水体）。判据必须是"多介质 且 有显式对比词"。

3.3 工具调用：8 个工具，每个都对应一类模型做不好的事

工具职责存在的理由
search_standard自然语言检索标准条文探索式查询，不知道标准号时用
get_clause按条文 ID 取原文禁止模型凭记忆复述条文，引用必须来自原文
check_standard_status ★标准时效性校验模型无法知道自己记的是哪一版；一票否决指标的执行者
lookup_limit结构化限值查询带适用条件的精确取值，不能靠阅读理解

trace_standard_chain ★替代链追溯"该用哪个版本"需要图遍历，不是检索问题
resolve_applicable_standard ★多标准适用优先级裁决国标/行标/地标冲突时，需要规则引擎而非相似度
classify_eia_category环评类别判定名录是规则表，判定是查表不是生成

适用优先级裁决的排序规则

依据《标准化法》与综合排放标准自身的适用条款，按五个维度依次排序：

  1. 时效性 —— 现行版本绝对优先
  2. 适用行业 —— 行业不匹配且非通用标准时降级
  3. 属地 —— 地方标准在本行政区域内优先适用
  4. 标准层级 —— 行业标准 / 地方标准优于国家综合标准
  5. 从严 —— 同分时取限值更小者
少一个维度就会"看起来有理、结论错误"

最初只实现了「时效性 + 属地 + 层级」三维。结果是：问"工业废水 COD 限值"， 系统回答了 DB33/ 2169-2018 的 30 mg/L —— 因为它是浙江地标、现行有效、层级更高。 但 DB33 2169 只管城镇污水处理厂，与工业废水无关，正确答案是 GB 8978 一级标准的 100 mg/L。 加入「适用行业」维度后才修正。这类缺陷指标不暴露就永远发现不了。

时效性校验必须由规划器无条件前置

关键设计：只要查询中出现标准号，规划器就无条件插入 check_standard_status， 不交给模型"判断要不要"。时效性违规是唯一的一票否决指标，不能有概率性—— 把业务规则写进系统提示是拦不住的，必须写进代码路径。

# 0) 硬约束前置：任何点名了标准号的查询，都必须先复核时效性
for r in slots.std_refs[:3]:
    plan.append({"tool": "check_standard_status", "args": {"std_id": r}})

# 引用生成处的硬过滤：废止标准只提示替代关系，绝不引用其原文
extra = [h for h in evidence_clauses.values()
         if ... and not h.get("is_stale")]

为什么数值类指标必须用规则判定

环保场景里限值 20 与 150 的差别就是合规与违法。 用 LLM-as-judge 打分会让"20 和 150 差不多"这种判断出现， 因此数值准确率、时效性违规率全部由确定性代码判定， LLM-as-judge 只用于开放式表述质量的辅助评估。

指标定义本身也会出错

正确拒答时本就不该有引用，但最初的 citation_precision 对空引用返回 0.0， 导致 4 道正确的拒答题系统性拉低引用精度（0.952 → 0.802 的差距就来自这里）。 修正为：按 should_refuse 判定是否记 N/A，而不是按"有没有引用"—— 否则会把真正的"漏引"也误判成 N/A，把缺陷洗成正常。

更严重的一类：指标替错误答案背书

"数值准确率"问的是「答案正文里出现过这个数吗」，不保证「结论就是它」。 裁决类问题（排入某水域执行几级标准、属地执行哪个标准）会把候选成套列进正文， 于是 Q006 的结论写着"三级 500 mg/L"、标注答案是"一级 100 mg/L"， 而数值准确率与要点覆盖率双双给出 1.0，端到端门禁判为通过。

这不是假想：该假通过在交付前的人工复核中发现，随后新增 结论一致率 专门盯"唯一结论"。修复后该题仍不及格，直到把定级规则补上才通过 —— 也就是说，这个指标确实抓住了一个真实缺陷，而不是把及格线调低了。

门禁也在静默失效

门禁配置里写的是 recall_at_5，聚合指标里叫 recall@5； 取不到值时旧代码 continue 跳过。结果是 7 个门禁里有 3 个从未真正生效 （recall_at_5 / tool_selection_accuracy / refusal_accuracy）。

它们当时恰好都达标，所以结论没错，但报告上"通过"与"没把关"长得完全一样。 现在改为：门禁引用了不存在的指标 = 配置错误 = 按不通过处理， 并在报告里显式打印"实际校验 N/M 项"。

3.5 闭环优化：归因必须能映射到动作

"跑一次评测"不叫闭环。闭环的判据是：评测结果能自动产出下一轮的具体修复清单。 本项目的归因引擎定义了 8 类缺陷，每类绑定确定的修复动作与责任层。

闭环的四步运转

  1. 评测：run_eval 跑全量黄金集，产出逐题明细与分类别切片
  2. 归因：diagnose 自动分类，按「时效性 → 拒答 → 数值 → 检索 → 规划 → 工具」排序输出修复清单
  3. 修复：按清单定向改动，改动范围限定在对应责任层
  4. 门禁：重跑评测，任一门槛未达标则不允许合入；stale_citation_rate > 0 直接一票否决
闭环最容易被忽略的价值

修复往往会引入新缺陷。本项目第 5 轮迭代就是被回归测试抓住的： 为了解决对比类问题新增了查询分解分支，判据写成"多介质"， 结果把"排入地表水Ⅲ类水域的工业废水"也误判成对比题，Q006 直接归零。 没有回归测试，这个劣化会静默上线。

迭代 2 是本项目最重要的一次修复

最初的实现把失效标准做成"顶部提示"，但条文原文仍然进入了引用列表。 提示与引用并存，用户复制走的依然是一段已废止的条文。 加上硬过滤后，时效性违规率从 8.3% 直接归零。 教训：时效性问题靠提示语拦不住，必须在数据结构层面拦截。

06边界与风险

明确说清楚这个系统不做什么、以及哪些结论必须回到官方文本核对。

系统边界

不做的事

· 不替代环评报告编制等专业产出
· 不给出执法级判定结论（需考虑监测方法、采样频次、数据有效性规定）
· 不提供超出知识库范围的推测性回答 —— 证据不足即拒答
· 不做跨省份地方标准的穷尽覆盖（按需增量接入）

必须回到官方文本的场景

· 环评类别判定（直接决定合规成本与审批流程）
· 达标判定用于正式用途时
· 任何涉及行政处罚、诉讼、验收的场景
· 地方标准与国家标准冲突且地标未收录时

已识别的风险与应对

风险等级应对
数据未逐条核验高schema 层强制 verified 标记；未核验数据在评测中单独统计；生产环境必须重新灌入官方文本
评测集代表性不足高24 题仅够验证管线，生产需扩至 200+ 题；P4 阶段用线上真实 bad case 回流扩充
标准更新导致知识库滞后中定期巡检官方标准库更新公告；替代链变更触发回归评测
解析规则随 PDF 版式变化失效中适配器按机构隔离，单点失效不影响其他数据源；入库时做结构校验
离线规划器覆盖面有限中规则规划器建立可复现基线，接入 LLM 规划器后做 A/B 对比，不达标不上线

运行方式

# 建索引
python -m src.kb.build_kb

# 单次问答（离线规则规划器，零 API 成本）
python -m src.agent.loop "浙江省的城镇污水处理厂COD执行什么排放限值"

# 全量评测 + 归因
python -m src.eval.run_eval
python -m src.eval.diagnose

接入真实模型只需在 src/config.py 中配置 LLM_PROVIDER 与 EMBED_PROVIDER，其余逻辑不变。离线模式的存在是刻意设计—— 它让评测闭环在没有 API 预算时也能运转，同时提供一个确定性的对照基线， 用于判断接入 LLM 后究竟是变好还是变差。
